### managed-multi-repo-bootstrap (E-013 - E-021)
- **E-013** - Approved repository set: `crates/axiom/src/bootstrap/repos.rs` (with the new `crates/axiom/src/bootstrap/` module tree and its `lib.rs` wiring) turns explicit solution bindings into an admission check instead of a lookup. A declared root must exist, be a directory, be readable, have exactly the declared repository directory name and - when the solution pins one - the declared canonical origin, or it is rejected with a stable rule (`repository-absent`, `repository-not-a-directory`, `repository-inaccessible`, `repository-name-mismatch`, `repository-remote-mismatch`, `repository-root-unsafe`, `repository-root-duplicate`, `repository-id-duplicate`). A similarly named checkout such as `axiom-graphd-old` can never stand in for `axiom-graphd`, a same-named fork is refused by origin, and unsafe (`..`, relative) or duplicated bindings are refused before any host read, so no repository is silently substituted. Observed state enters through `RepoProbe`; `LocalRepoProbe` reads metadata and `.git/config` (a `.git` directory or a worktree `.git` file with `gitdir`/`commondir`) and never writes. A partial set is a result rather than an error - unaffected repositories proceed and refusals are reported - while a solution with nothing approved is refused with `solution-has-no-approved-repository`.
- **E-014** - Managed marker parsing: `crates/axiom/src/bootstrap/markers.rs` finds the single owned span between `<!-- axiom-graph:begin -->` and `<!-- axiom-graph:end -->` and refuses anything ambiguous, so the writer never guesses. Marker text inside a Markdown code fence (``` or ~~~, up to three leading spaces, a closing run at least as long with a blank remainder) is a quoted example and is ignored; a marker line is recognised after trimming surrounding whitespace, and a leading UTF-8 BOM neither hides the first marker nor becomes part of the span. A lone marker is refused `markers-unbalanced`, more than one pair or a doubled begin/end is refused `markers-duplicate`, and an inverted span is refused `markers-out-of-order`; every refusal is a `MarkerConflict` value rather than a byte range, and the parser is read-only, so refusing never alters human text. The whole `fixtures/bootstrap` corpus is replayed by the tests: the four marker-conflict vectors are refused and `markers_in_fence` yields no marker outside its fence.
- **E-015** - Encoding- and newline-preserving text handling: `crates/axiom/src/bootstrap/text.rs` makes "change only the owned span" a type instead of a habit. `SourceText::decode` accepts a UTF-8 document with an optional single leading BOM and refuses any other encoding with a conflict carrying the stable rule `text-encoding`, leaving the caller's bytes untouched; `SourceText::encode` returns those bytes verbatim, so the corpus before-states round-trip byte for byte. The dominant newline (`\r\n` when the document contains one, `\n` otherwise) is also the newline of the written block, and `render_block` trims the template's surrounding newlines and re-expresses it in that convention, so a CRLF repository is never converted to LF and an LF repository never gains a CRLF. `replace_span` splices the block between the bytes before and after the span (a leading BOM therefore stays outside it and is never re-encoded), `append_block` keeps the whole original document as an exact prefix and inserts one newline when the file already ends with one or a blank separator line otherwise, and `replaces_only_span` states the preservation property once for the planner, applier and verifier. A span that does not fit or is inverted is refused with `text-span-out-of-range` rather than clamped. The whole `fixtures/bootstrap` corpus is replayed: 12 before-states round-trip, zero are refused, the four append vectors keep their original bytes as a prefix and the two replace vectors change nothing outside their span.
### documentation-guides (D-012 - D-014)
- **D-012** - Git checkpoint and merge guide: `docs/guides/git-checkpoints.md` separates the three states an operator conflates - live ignored data under the project output root, the optional staged export that only an explicit checkpoint command writes, and merged-source regeneration after the source merge is final - and states the rule that makes the rest safe: a generated graph is never merged, it is regenerated from merged source. It fixes the source selection (index bytes by default, a stability certificate for the worktree, a pinned commit for CI), the four-step merge order (resolve source, regenerate, validate catalog references, run tests), the refusals that must stay refusals (union merge, hand-picking a graph side, a worktree fallback for a path missing from the index, `WORKTREE_BUSY` at exit 6, `NOT_READY` at exit 4 for a stale checkpoint) and the size budgets. The page states plainly that the checkpoint argv surface is not implemented at this revision, that tasks E-023, E-024, E-025 and F-021 are still `todo`, and that this guide has no Rust oracle: `fixtures/guides/driver.py` is the only executed check, and the `absent_paths` list in `fixtures/guides/manifest.json` fails the driver if the absent oracle ever appears without the guides being updated with it.
- **D-013** - Multi-repo bootstrap operations guide: `docs/guides/bootstrap.md` defines the two owned artifacts (the small pointer block in `AGENTS.md` and the canonical `.axiom/agent/POLICY.md`) and the managed-merge algorithm's exactly-one outcome per repository - **append** when the file is absent or has no markers, **replace** only the block whose hash matches the last applied hash, **adopt only** through an explicit plan, **conflict** on duplicate, missing, nested or out-of-order markers, on a human edit inside the owned block, on a whole-file policy edit or on a manifest that names a missing policy, and **unchanged** when a re-apply would change nothing. Plan is read-only and is not approval; apply re-verifies root bindings, ownership and before-hashes and refuses a stale or digest-less plan. Conflict always means refuse and preserve: bootstrap never truncates, relocates, appends a second block, recursively deletes `.axiom`, overwrites unowned content or auto-discovers every repository under `HOME`, and `POLICY.local.md` is the human override path. The page states plainly that the bootstrap engine (E-013 to E-034) is not implemented at this revision, records `axiom bootstrap` as a recognised verb that refuses with `NOT_READY` (exit 4) with that mapping source-verified rather than observed, and notes that this guide has no Rust oracle.
- **D-014** - Version update and rollback guide: `docs/guides/updates.md` gives every component (axiom-graphd, axiom-mcp, the bundled axiom CLI, the skills bundle, and the docs/fixtures that inherit their owner version) a check route, an update route and the trust that route requires, and states the two rules that decide the rest: a branch is never `git pull`-ed and executed, and a checksum is not proof of publisher. Trust is a signed metadata chain with a pinned root, an approved plan digest and a verified backup; an unsigned, untrusted, signature-expired, schema-newer or backup-missing candidate is refused with a named reason rather than installed, auto-apply defaults off, an offline check reports stale rather than "up to date", and a post-update health failure rolls the version pointer back and restores a compatible backup. The page states plainly that the updater (E-035 to E-045) is not implemented as a command, that the `update` and `skills` verbs are recognised-and-refused (`NOT_READY`, exit 4), and that the executed evidence is `fixtures/update/driver.py` (exit 0, `provenance_verified: false`) plus `fixtures/guides/driver.py`, with no Rust oracle at this revision.

### install-pipeline (E-004, E-005, E-006, E-007, E-008, E-009, E-010, E-011, E-012)
- **E-004** - `crates/axiom/src/install/plan.rs` plans one installation from a verified local bundle without touching the host: it opens and reads `bundle.json` read-only and is otherwise pure over its inputs, so the dry run reports component versions and actions, absolute destination and staged-destination paths, download sources with declared digests and `executed: false`, the required permissions, the announced service change and the planned network access - and performs no write, download, launch or elevation. A per-user plan refuses an `elevated` permission, a system mechanism outside a system scope and a system-scoped plan with no explicit opt-in; two components planning the same destination, an artifact built for another host, a version that is not a safe path segment and an artifact path that escapes the bundle are refused; a missing bundle manifest is `NotFound` while a malformed one fails closed, and the plan seal binds approval to the exact plan body. The `install_plan_probe` example runs the same planner on a real fixture, prints the plan and leaves the install root uncreated (`install_root_present=no`). `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings` and `cargo test -p axiom --lib --locked` all exit 0 in `axiom-rust-git:1.85`.
- **E-005** - `crates/axiom/src/install/verify.rs` is the fail-closed trust gate between a downloaded artifact and its execution: the release's trusted metadata (an `ed25519`-only algorithm allowlist, published trust roots, and a per-artifact digest, size, host and expiry) and the actual bytes must agree before anything is executed. Bytes that disagree with the trusted digest or size, an unsigned artifact, a key that is not a published trust root, a non-allowlisted algorithm (refused as `Forbidden` on the artifact and as malformed-metadata `ValidationError` on a root), an artifact built for a host this install does not accept and a release evaluated at or after its expiry are all refused; one bad member refuses the whole bundle instead of returning a partial verified set. `signing_message` binds every trusted property, not only the digest, so a signature cannot be replayed under another component, version, host or location.
- **E-006** - `crates/axiom/src/install/apply.rs` activates a verified staged version atomically with rollback metadata: every payload that needs activating is read from staging and checked against its declared digest and size before the first mutation, then payloads are moved and the `current` pointer is replaced through a sibling temporary, so a reader sees the previous install or the new one and never a torn combination; each transaction writes a journal entry and a rollback record naming the pointer it replaced and the previous-version depth. Approval binds to the exact canonical plan digest, so an approval of one plan can never activate another. A partial staging tree, a staged payload that disagrees with its digest, a destination that already holds different bytes and an approval for another plan all refuse the transaction and leave the install untouched (asserted against an in-memory `InstallFs` double), while a destination already holding the same bytes is reported `already_present` and not rewritten; the real `LocalFs` adapter is exercised under a temporary root.
- **E-007** - `crates/axiom/src/install/credentials.rs` mints the two scoped local credentials an install needs and nothing more: `CredentialRole::Mcp` is an `mcp` audience with a single `read` scope and `CredentialRole::Daemon` is a `control-api` audience with `read`, `reconcile`, `checkpoint-write` and `verify`, and no role ever carries `admin`, so the daemon control surface from `axiom_graphd::control::auth` (task B-083) accepts them without a second contract. Secrets come from an injected `EntropySource` (production `OsEntropy` reads the OS CSPRNG) and are held in a `Secret` that is neither `Serialize` nor printed - its `Debug` is `[redacted]`, its `Drop` overwrites the buffer, and a rendered credential is scrubbed by `graph_core::redact::scrub_for_export`; only a digest-only `CredentialIndex` is persisted, under a `credentials/` directory the crate refuses to place inside a Git worktree and excludes from diagnostic bundles. An all-zero or stuck entropy source, a draw shorter than the minimum, a duplicate role, a set that grants `admin`, an index edited to swap an audience or add a second role, a set generated for another install root and a plan with no credential-bearing component are all refused with a named reason, while the production entropy source is asserted to return fresh 32-byte secrets. The module reuses the frozen `ControlToken`/`TokenRegistry` contract in an integration test, so `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo build --locked` and `cargo test --workspace --locked` all exit 0 in `axiom-rust-git:1.85`.
- **E-008** - `crates/axiom/src/service/windows.rs` is the Windows per-user startup adapter: `plan_task` renders a Task Scheduler XML for a component with a per-user logon trigger, an `InteractiveToken`/`LeastPrivilege` principal, an optional bounded `RestartOnFailure` policy and a log file that must live under the install root, and `install_task` registers it through an injected `ServiceExec` (program plus argv, never a shell string). The "no silent machine-wide elevation" rule is structural: a system-scoped request and an explicit elevation request are both refused `Forbidden` before anything is rendered, the principal is fixed at least privilege, and registering requires a separate `Consent` token, so a front end cannot elevate or register by accident. A foreign task name is refused by `start`/`stop`/`status`/`uninstall` so the adapter never touches another application's task, and a NUL-bearing argument, a relative path, an unknown component, a log file outside the install root and an out-of-range restart policy are refused with a named reason; the Windows mechanism stays per-user, so a system-scoped or elevated request never reaches the scheduler. `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo build --locked` and `cargo test --workspace --locked` all exit 0 in `axiom-rust-git:1.85`. Native Windows runtime evidence is not produced on this host (no native MSVC toolchain and Docker is Linux); the 18 new tests exercise the rendered definition and every refusal, and the scheduler call is a trait double.
- **E-009** - `crates/axiom/src/service/linux.rs` is the Linux per-user startup adapter: `detect_user_systemd` decides whether a managed `systemd --user` unit can be installed from an injected `SystemdProbe` (a `--user`-capable `systemctl`, an absolute `XDG_RUNTIME_DIR` and an existing session-bus directory), and `install_unit` refuses with `NotReady` when any of those is missing, naming the documented foreground fallback (`axiom-graphd serve --registry <registry.json>`) in the message and in the `expected` detail, so the installer never claims a managed service it did not create. `plan_unit` renders a per-user unit under `~/.config/systemd/user/<component>.service` with `WantedBy=default.target`, `StandardOutput`/`StandardError=append:` to a log file under the install root, and an optional bounded `Restart=on-failure` with `RestartSec` and `StartLimitBurst`; a system-scoped or elevated request is refused `Forbidden`, and a foreign unit is refused by `enable`/`start`/`stop`/`status`/`uninstall`. The `ServiceExec`/`ServiceOperation`/`ServiceOutput`/`SysExec` and `InstalledService` contracts and the `is_under` helper now live in `service/mod.rs` and are shared by both adapters. `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo build --locked` and `cargo test --workspace --locked` all exit 0 in `axiom-rust-git:1.85`. Native Linux runtime evidence is `not_run`: the Docker gate host is a container without a user session bus, so detection, rendering, every refusal and the controller call are exercised against trait doubles instead.
- **E-010** - `crates/axiom/src/service/macos.rs` is the macOS per-user startup adapter, the launchd agent `21-INSTALLATION.md` section E pins: the label is `com.axiom.<component>` and the plist is always rendered under the caller's own `~/Library/LaunchAgents`, so a foreign label, a relative path, a plist outside the user agent directory and a label that is not exactly one of the installable components are refused with a named reason before anything is rendered - an invalid configuration therefore yields no `launchctl` operation and no file to delete (`plan_removal` returns `Ok` only for the owned label and the owned plist, and its `operations`/`files` name that one plist). A system-scoped or elevated request is `Forbidden` before rendering; a relative executable, working directory, install root or home is refused, as is a log file outside the install root, an argument carrying a NUL byte and an out-of-range restart policy. The rendered property list declares `Label`, `ProgramArguments`, `WorkingDirectory`, `RunAtLoad`, `StandardOutPath`/`StandardErrorPath` and `AXIOM_INSTALL_ROOT`, and an on-failure policy becomes a bounded `KeepAlive` dict with `SuccessfulExit=false` plus a `ThrottleInterval` rather than an unbounded respawn. Installation goes through the injected `ServiceExec` boundary (program plus argv, never a shell string) and a non-zero `launchctl` exit is reported `Internal`/`controller-exit`. macOS native runtime evidence is `not_run`: this lane's verification host is a Linux container with no macOS launchd user session, so the adapter is implemented and unit-tested against the card (13 positive, negative and boundary tests) and no native macOS behaviour is claimed; `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo build --locked` and `cargo test --workspace --locked` all exit 0 in `axiom-rust-git:1.85`.
- **E-011** - `crates/axiom/src/service/control.rs` is the one host-neutral control surface over the three adapters: a control command starts from the `InstalledService` the adapter returned and `ServiceOwnership::claim` re-derives the registered name from the component with the same adapter that created it, so a name that does not match its component (`ownership-mismatch`), an unknown component, a system scope, the unmanaged `SystemService` mechanism and a definition outside the directory that mechanism owns for the user are all refused - a command cannot be aimed at another component's instance or a foreign name, and each adapter then re-checks ownership itself before rendering. PID reuse cannot target another process: no rendered operation ever contains a pid, a pid is accepted only through `bind_process`, which mints the ownership token from the identity of the definition the process was observed running, and `plan_process_stop`/`ProcessRef::verify` refuse any token that names another definition - so a pid recycled by a later process, a pid bound to another component's definition or another install root, and `pid=0` are all refused, while the matched pid is still never rendered into the operation because the controller acts on the owned name. `run_control` distinguishes the two controller semantics the host actually has: a non-zero exit from `start` or `stop` is `Internal`/`controller-exit` because the instance was not controlled, while a non-zero exit from `status` is carried in the `ControlOutcome` as an observation, since `systemctl --user status` and `schtasks.exe /query` both exit non-zero for a stopped or absent instance. 13 targeted positive, negative and boundary tests pass.
- **E-012** - `crates/axiom/src/install/uninstall.rs` plans the uninstall of the runtime components one install owns, keeping the removal classes separate (services, runtime, bootstrap blocks, credentials, cache, user data) and preserving human content by default: project source, annotations, checkpoint JSON and user instructions are always named as preserved, and the plan removes only paths inside the install root, never the uninstall report it keeps beside them. A default plan removes the four owned classes and neither cache nor user data; cache is purged only under an explicit `with_cache_purge`, and user data only when the caller presents a `PurgeApproval` minted by `PurgeApproval::explicit`, so an unapproved purge is `Forbidden`. A relative or escaping runtime path, a path outside the install root, a bootstrap block whose id is not `axiom:`-prefixed, a removal that overlaps a preserved path, a relative preserved path, a request that names nothing and a reserved report path are all refused with a named reason; a service instance is refused unless `ServiceOwnership::claim` accepts it (a mismatched name is `ownership-mismatch`, a definition outside the mechanism-owned directory is `definition-outside-owned-directory`, and a system instance is `Forbidden`/`unsupported-scope`). `run_uninstall` drives the controller and has no file-removal path by design, reports a non-zero controller exit as `Internal`/`controller-exit`, and renders a report that lists the removed classes with the preserved set. `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo build --locked` and `cargo test --workspace --locked` all exit 0 in `axiom-rust-git:1.85`.
