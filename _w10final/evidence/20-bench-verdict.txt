--- MEASUREMENT CAVEAT (real, from our own tooling) ---
mcp_stdio_client.py collects responses with a time.sleep(0.02) poll loop, so each per-query
elapsed_ms is quantised into ~20 ms buckets. Single-query latency is only good to about +/-20 ms.

--- ONE-OFF COSTS (so amortisation is explicit, not hidden) ---
cold first `serve`, full analysis (inventory_added=473, analyzed_files=473, nodes=1368, edges=1213)
      = 16720 ms   (first ever build, cold page cache)
warm full `serve` on the same tree            = 9227 ms   (re-run, warm cache)
incremental `serve` after a ONE-file edit      = 445 ms
incremental `serve` after restoring that file  = 313 ms
=> re-analysing after a small edit is ~0.3-0.5 s, i.e. ~20-50x cheaper than the cold build.

--- WHERE THE REAL WIN IS (measured slope + clearly-flagged extrapolation) ---
The no-graphd leg is a full text scan, so its cost is LINEAR in the number of source files.
Measured on real files at several prefix sizes (evidence/21-scan-scaling-r{1,2}.out):
   run r1: slope 0.228 ms/file -> break_even 386 files
   run r2: slope 0.437 ms/file -> break_even 201 files
   (earlier sample:        0.372 ms/file -> break_even 186 files)
=> break_even_files ~= 200..390 source files, in EVERY sample ABOVE this repository's 156 files.
   That is exactly why the two legs are at parity here: the repo sits below the break-even point.
   Above ~200-390 source files the scan cost keeps growing while one graph_query round trip stays
   roughly constant, so graphd starts to win.
NOTE: break_even_files is a DERIVATION from a measured slope, NOT a scan of a 200+ file tree.

--- WHAT GRAPHD SAVES AT THIS SIZE (honest) ---
Not seconds of latency. The text leg can only list members; it cannot answer "what depends on
this", and it has no node identity, no kinds, no resolution and no evidence. Answering those by
scanning needs further full-tree greps. graphd answers them in ONE ~58-118 ms call from a stored
graph, plus a 0.3-0.5 s incremental refresh after an edit instead of a rescan.
