### ecosystem-install-orchestration (I-004)

- **E-015** - Encoding- and newline-preserving text handling: `crates/axiom/src/bootstrap/text.rs` makes "change only the owned span" a type instead of a habit. `SourceText::decode` accepts a UTF-8 document with an optional single leading BOM and refuses any other encoding with a conflict carrying the stable rule `text-encoding`, leaving the caller's bytes untouched; `SourceText::encode` returns those bytes verbatim, so the corpus before-states round-trip byte for byte. The dominant newline (`\r\n` when the document contains one, `\n` otherwise) is also the newline of the written block, and `render_block` trims the template's surrounding newlines and re-expresses it in that convention, so a CRLF repository is never converted to LF and an LF repository never gains a CRLF. `replace_span` splices the block between the bytes before and after the span (a leading BOM therefore stays outside it and is never re-encoded), `append_block` keeps the whole original document as an exact prefix and inserts one newline when the file already ends with one or a blank separator line otherwise, and `replaces_only_span` states the preservation property once for the planner, applier and verifier. A span that does not fit or is inverted is refused with `text-span-out-of-range` rather than clamped. The whole `fixtures/bootstrap` corpus is replayed: 12 before-states round-trip, zero are refused, the four append vectors keep their original bytes as a prefix and the two replace vectors change nothing outside their span.
- **E-016** - The separate managed policy file: `crates/axiom/src/bootstrap/policy.rs` fixes both properties a pointer block needs. First, the managed block must actually point somewhere - `block_points_at_policy` requires the literal `.axiom/agent/POLICY.md` and the word `read`, so a block that only mentions the path in prose, says `readme`, or names no policy at all is refused with `policy-pointer-missing` instead of written; the shipped block template and the policy template are asserted directly, and the policy's own `Managed policy version:` line is parsed so the version recorded in the ownership manifest can be read back out of the file. Second, a policy file is only ever managed when an ownership manifest records its digest: `PolicyVerdict` decides `Create`, `Unchanged`, `Edited`, `Unowned` or `Removed` from the observed and recorded digests, and the unowned case is decided *before* the digest is compared, so a pre-existing `.axiom/agent/POLICY.md` is never adopted and never overwritten even when its bytes are byte-identical to the shipped template - it is refused `policy-unowned`. A human edit to an owned policy is `policy-edited` and a removed owned policy is `policy-missing`; both refuse and preserve, and `.axiom/agent/POLICY.local.md` stays the human override path bootstrap does not own. The corpus is replayed: exactly the three vectors whose reason is `unowned` or `policy` are refused, nine before-states create the policy and four already match.
- **E-017** - Ownership hashes and template version: `crates/axiom/src/bootstrap/ownership.rs` writes `.axiom/agent/bootstrap.lock.json` as the record of exactly two artifacts - the managed span of `AGENTS.md` and the managed policy file - plus the template version that produced them, and nothing else. The single constructor `Ownership::new` computes both digests from the bytes it is handed, so the manifest cannot claim ownership of content bootstrap did not write, and the record is a fixed four-key document with no per-path map, listing or timestamp to drift out of date. `parse` refuses a manifest this build cannot trust rather than half-understanding it: unreadable or truncated JSON and non-UTF-8 bytes are `ownership-malformed`, an unknown schema version or empty template version is `ownership-schema`, and a digest that is not a canonical lowercase SHA-256 is `ownership-digest`. `detect_drift` then recomputes both digests from the repository before any update, so a human edit inside the owned block is `ownership-block-edited` and a removed block is `ownership-block-removed` (checked first, as the contract's decision order requires), while an edited or removed policy is `ownership-policy-edited` / `ownership-policy-removed`; each refusal carries the word the contract uses for that failure and preserves the human bytes. The corpus is replayed: all six before-states that carry a manifest re-encode byte-identically - which is what makes a re-apply a no-op - and exactly the three drifted vectors are refused, while the three still-current ones stay current.
- **E-018** - Reviewable multi-repository plans: `crates/axiom/src/bootstrap/plan.rs` turns the per-slice verdicts into one document an operator can read before anything is written, and the read-only property is structural rather than promised - `RepositoryReader` has a single method that can only read, `LocalRepositoryReader` is the only filesystem adapter and its only filesystem call is `fs::read`, so planning a repository that has no `.axiom` directory cannot create one (asserted against a real temporary directory, whose recursive listing is unchanged afterwards). Each repository in the plan carries its change classification (`append`, `replace`, `unchanged` or `conflict`) exactly as `fixtures/guides/bootstrap.md` names them, the managed-block hash before and after, and, for every file it would write, the destination-relative path, the before- and after-SHA-256, the exact bytes and a proposed unified diff; `render` prints the whole thing for review and `conflicts` lists the refusals. Refusals do not abort the run: a marker shape, markers without ownership, a non-UTF-8 file, an unowned policy and a human edit inside the owned block each become a `conflict` entry carrying the stable rule from `markers`, `text`, `policy` or `ownership`, while unaffected repositories are still planned, so the aggregate can report per-repository outcomes and exit 20 for a partial run. A plan is bound to its inputs: the digest is a SHA-256 over the canonical bytes of the document with the digest field empty, `to_canonical_bytes` is what an operator approves and `parse` refuses a body that no longer hashes to its recorded digest (`plan-digest-mismatch`), so a plan edited after approval cannot be applied. The whole corpus is replayed through the real adapter: five append, two replace, one unchanged and eight conflicts, each matching its documented outcome and reason.
- **E-019** - Before-hash verification and the per-repository apply lock: `crates/axiom/src/bootstrap/preconditions.rs` makes "re-check the before-hashes, then take the lock" a checked precondition instead of a promise. `verify_repository` re-reads every file the plan would write, compares its current SHA-256 with the `before_sha256` the plan recorded, recomputes the managed block from the current `AGENTS.md` and compares that with the plan's `before_block_sha256`, and refuses any mismatch with the stable rule `plan-stale` naming the field, the expected and the observed hash - so a plan whose inputs changed after approval is rejected before its repository is written, and an `unchanged` repository whose block was edited is caught even though the plan proposes no file. The bound root must still be a directory (`precondition-root`) and a repository the plan already refuses is rejected (`plan-repository-conflict`). `ApplyLock::acquire` creates one lock file per repository under `AXIOM_HOME/bootstrap-locks/<id>.lock` with a create-only exclusive open, so a cooperating apply that races the same repository loses with `apply-lock-held` (`WorktreeBusy`) and is told who holds it rather than overwriting the holder's token; an identifier that could escape the lock directory is refused `apply-lock-id-unsafe`, and the lock is removed only while it still records this holder's token, so dropping a failed apply releases it and no process deletes another's lock. `begin_apply` composes the two in the guide's order - lock first, then re-verify, releasing the lock when the verification refuses - and `PreconditionHost` keeps the policy host-free: `LocalPreconditionHost` is the only filesystem adapter and an in-memory double exercises every refusal. Tests cover the positive verify-and-release, a stale target, two applies that cannot interleave and then proceed once released, a foreign lock that is preserved, unsafe identifiers, an unbound root, a conflict plan and a real lock taken and removed by the production host.
- **E-020** - Journaled, backup-protected application: `crates/axiom/src/bootstrap/apply.rs` is the only half of bootstrap that writes, and it is built to fail safely. Per repository it takes the apply lock and re-verifies the before-hashes (E-019), backs the affected bytes up under `AXIOM_HOME/bootstrap-backups/<id>/`, writes a `bootstrap-journal/<id>.json` *intent* before touching an owned file, writes the owned files with `.axiom/agent/bootstrap.lock.json` last, verifies the written hash against the approved after-hash and recomputes the bytes outside the managed block, and only then marks the journal complete. A write that fails rolls back: every file this run already wrote is restored from its backup, and a file whose current hash no longer equals the after-hash this run wrote is left untouched and reported (`RollbackRefused`) rather than discarding a newer human edit; a missing backup is refused `apply-backup-missing`. The aggregate applies one repository at a time and reports every repository independently - `Applied`, `Unchanged`, `Refused` (a plan conflict or a stale/locked precondition), `RolledBack` and `RollbackRefused` - with `exit_code()` returning `PartialOperation` (20) when some repositories were updated and others were not, so bootstrap never claims all repositories were updated when only some were. `BootstrapHost` keeps the write path host-free: `LocalBootstrapHost` writes through a temp file and rename, and `MemoryBootstrapHost` can make a chosen write fail so rollback and the refused-rollback boundary are exercised. Tests cover the applied-and-journaled path, a failed write that restores the earlier file and leaves the failing one absent, a rollback that refuses to discard a newer edit, a two-repository run that reports one stale refusal and one success at exit 20, a conflict plan refused without a write, the outside-content comparison and a real apply through the production host.
- **E-021** - Idempotence and drift reporting: `crates/axiom/src/bootstrap/verify.rs` is the read-only close of the bootstrap loop and the gate that tells a managed edit apart from a human one. It re-plans the repository from its current bytes (E-018) and classifies it: `current` when the plan is `unchanged`, which is exactly the statement that a second apply writes nothing; `managed-refresh` when the owned content is intact but a template update would rewrite the block or policy in place; `unbootstrapped` when no ownership manifest exists yet; `managed-drift` when the bytes *inside* the managed block or the policy file no longer match the manifest (`ownership-block-edited`, `ownership-block-removed`, `ownership-policy-edited`, `ownership-policy-removed`); and `undecidable` for a marker shape or ownership record bootstrap will not judge. A change *outside* the managed block is reported in `human_edits` and never fails the run - bootstrap did not own those bytes and `owns_only_the_managed_span` proves the proposed write could not touch them, allowing only a span replacement or an append that keeps the whole human document as an exact prefix and refusing anything else with `verify-outside-content-changed`. `VerifyReport::exit_code` is 0 for a clean run even when a second apply would write, the drift's own status when every repository drifted, and `PartialOperation` (20) when only some did, so a partial result is never reported as a whole one. `VerifyTarget` carries the approved pre-apply snapshot so the human-edit baseline is the plan's own input; tests cover the no-op second apply, the outside-edit-versus-inside-edit distinction, a policy-only drift, an undecidable marker shape, an unbootstrapped repository, the partial exit 20 and the write-scope boundary.

### managed-multi-repo-bootstrap (E-022 - E-025)
- **E-022** - Version-gated managed update: `crates/axiom/src/bootstrap/update.rs` decides whether a repository's managed content may move to the template this build ships. `TemplateVersion::parse` reads a strict `MAJOR.MINOR.PATCH` with an optional pre-release and a manual SemVer precedence in which a release outranks its own pre-release (`1.2.0` is newer than `1.2.0-rc.1`) while two pre-releases compare lexically, so the ordering is not the derive-order of `Option` and a downgrade cannot masquerade as an update; the malformed shapes around it (`1`, `1.2`, `1.2.x`, `1.2.-1`, `1.2.3-rc..1`) are refused with `update-version-invalid`. `compatibility(installed, shipped)` returns `newer`, `same`, `downgrade` or `major-change`, and `require_compatible_template` refuses a downgrade (`update-downgrade`) or a different major (`update-major-change`) *before* any repository is read, so an unacceptable template can never produce a partial update. `plan_update` then emits one row per repository through the reviewable plan (E-018): `updated`/`unchanged`/`skipped`, a `remaining` list, `is_complete`, a rendered review and a `to_bootstrap_plan` hand-off, and it only ever plans the three paths bootstrap owns - a plan that would write an unowned path is refused `update-unowned-path`, and an `AGENTS.md` change that alters bytes outside the managed span, or an append that does not keep the previous document as a prefix, is refused `update-outside-owned-span`. ### secure-check-update-rollback (E-042 - E-048)
- **E-042** - Rust binary activation: `crates/axiom/src/update/rust_binary.rs` activates a staged payload by moving a pointer, never by replacing a running image. `StagedVersion` carries the version, the 64-hex digest the staged bytes must have and the smoke-check flag, and `BinaryActivation::activate` refuses a payload that is missing, whose bytes do not match that digest, that was never smoke checked, or whose version is not one safe path segment; the pointer is written as a temporary sibling and renamed, so a failed move leaves the previous pointer byte-for-byte intact and `launch_target` still resolves the previous binary. Everything mutating goes through the small `ActivationFs` trait (exists/read/write/rename) so the module cannot delete, truncate or spawn, and a hostile fixture cannot make it do more than write one temporary file and rename it. 12 positive, negative and boundary tests; `RUNNING_IMAGE_IS_LOCKED` records that replacing a running image is impossible on Windows, so no code path attempts it.
- **E-043** - Python/MCP environment activation: `crates/axiom/src/update/python_env.rs` builds and activates the interpreter environment from a locked, versioned directory instead of mutating the active environment in place, so an interrupted build cannot leave a half-updated environment serving traffic. The lock file pins the requirement set and its digest, the build is refused when the lock, the interpreter identity or the wheel set does not match what the plan approved, and activation is the same atomic pointer move as E-042; the doubling surface is an `EnvFs` trait with in-memory doubles. 12 positive, negative and boundary tests.
- **E-044** - post-update doctor: `crates/axiom/src/update/verify.rs` probes health, handshake, graph/queue schema and a fixture query through a `ProbeRunner` boundary and turns a failure into a *bounded* rollback instead of a superficial success. A non-2xx status, a body that is not the expected document, a handshake protocol or version mismatch, missing capabilities, a schema mismatch, a transport error and a too-large body are each a named rule; `Expectations::core` derives the expected protocol and schema set from `crate::version`, and a probe set that cannot be derived (`expectations_incomplete`, `expectations_protocol_version_absent`) is refused rather than guessed. `DoctorVerdict::Rollback` carries the failing rules plus the scope, and `RollbackStep` is the closed set of steps a doctor may ask for (`StopNewProcess`, `RepointPrevious`, `RestoreCompatibleBackup`, `ClearUnpublishedOutbox`). 10 tests.
- **E-045** - state-aware rollback: `crates/axiom/src/update/rollback.rs` treats binary, database schema and policy as one compatible set. `VersionSet` and `Snapshot` (with its backup digest and verified flag) describe where the host is, `Compatibility` decides from the release set, migrations and the policy floor whether a downgrade is `Reversible`, `Irreversible` or `Missing`, and `RollbackPlan` names the steps, whether reconciliation is required and whether the verify journal must be consulted; `restores_one_set` is true exactly when a schema move is accompanied by the `RestoreCompatibleBackup` step, so a plan can never claim to restore a set while dropping the backup it depends on. A `RollbackScope` other than the full set is refused (`partial_rollback_refused`) rather than half-applied. 9 tests.
- **E-046** - update policy: `crates/axiom/src/update/policy.rs` decides `ApplyAutomatically`, `RequiresApproval` or `Refused` and defaults to explicit approval.
